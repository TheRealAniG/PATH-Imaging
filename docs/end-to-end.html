Section 02 · Sensor

What a camera sends

A sensor is a grid of light detectors called pixels. During the exposure each pixel collects light, then reports one number saying how much it got. A frame is the full grid of numbers from one exposure.

Our cameras report 10-bit numbers. Ten bits can count from 0 (no light) to 1023 (as bright as the pixel can record). This is the bit depth, and frames in this form are called RAW10. "Raw" means the numbers come straight from the sensor. Nothing has adjusted brightness or colour.

Most cameras do not hand out raw numbers. An ISP (image signal processor) first turns them into a finished picture and outputs a video format such as YUY2 or UYVY. The TEVS has an ISP on board. We ask it for RAW10, which bypasses the ISP, because the project needs the sensor's own values. One consequence: the TEVS's automatic exposure lives in that ISP, so in RAW10 we set the exposure by hand.

ReadImage sensor · Raw image format · Image processor (ISP) · Colour depth · Exposure (all Wikipedia)

Colour sensors see one colour per pixel

A pixel cannot tell colours apart. A colour sensor puts a tiny red, green or blue filter over each pixel, in a repeating 2 × 2 layout called the Bayer pattern. The IMX412C's order is red, green on the first row and green, blue on the second, written RGGB. Working out full colour for every pixel from this mosaic is called demosaicing.

Ten bits stored in sixteen

Computer memory is organised in bytes of 8 bits. A 10-bit value does not fit in one byte, so each pixel is stored in a 16-bit word (2 bytes). The value sits in the top ten bits.

Section 03 · Cable

From the sensor to the computer

Each camera connects with a flat ribbon cable that carries two separate things.

  • Pixels travel over MIPI CSI-2, the standard camera link on small computers. The data moves on lanes. A lane is one pair of wires carrying a fast serial stream. A camera can use 2 or 4 lanes at once, and more lanes carry more data per second.
  • Settings travel over I2C, a slow two-wire bus. The driver uses it to identify the camera and to write values such as exposure and gain into it. Every chip on the bus has an address: the IMX412 sensor answers at 0x1a, the TEVS at 0x48.

ReadCamera Serial Interface (Wikipedia) · MIPI CSI-2 specification overview (MIPI Alliance) · I2C tutorial (SparkFun) · I²C (Wikipedia)

WatchIntroduction: MIPI-CSI-2 Allied Vision · An Introduction to MIPI D-PHY (the lanes) MIPI Alliance · I2C protocol overview Texas Instruments

Why lanes set the top frame rate

The IMX412C module runs each lane at 1350 Mbit/s. One full frame is 4032 × 3040 × 10 bits, about 123 Mbit of pixels. Two lanes can carry that about 20 times a second, four lanes about 40.

On the Jetson Orin Nano board, the CAM0 connector has only 2 lanes and CAM1 has 4. The colour camera is on CAM0 today, which is why it tops out at 20 fps there. Swapping the two cables and reinstalling with sudo bash jetson/install.sh --imx412-on cam1 gives it 4 lanes. That puts the TEVS on 2 lanes. untested

Section 04 · Kernel driver

Inside Linux

The kernel is the core of the operating system. It is the only software allowed to talk to hardware. Everything else, including Python, the terminal and our UI, is an ordinary program that has to ask the kernel for what it needs.

  • A driver is the piece of kernel code that knows how to run one kind of device. Each camera has its own.
  • Our drivers are kernel modules: files ending in .ko that the kernel loads when it boots, such as tevs.ko and vc_mipi_camera.ko.
  • At boot each driver probes: it checks over I2C that its camera answers. The result goes into the kernel log, which you read with dmesg or journalctl -k.

The device tree: telling the kernel a camera exists

A camera on a ribbon cable cannot announce itself. The kernel learns it is there from the device tree, a description of the board's hardware: which port, how many lanes, which I2C address. An overlay is a small add-on to the device tree. Ours adds the two cameras. Source files end in .dts and are compiled to .dtbo.

V4L2 and ioctl

V4L2 (Video4Linux2) is the kernel's standard interface for cameras. Every camera driver answers the same set of commands, so one program can drive any camera.

When a program opens a device file, the kernel hands back a file descriptor: a small number that stands for the open file. To send a command, the program calls ioctl ("I/O control") with three things: the file descriptor, a request code saying which command, and a block of bytes holding the command's data. The kernel can write results back into the same block.

ReadVideo for Linux API (the kernel's V4L2 reference) · Video4Linux (Wikipedia) · ioctl(2) manual page · ioctl · File descriptor (Wikipedia)

Section 05 · Buffers

Getting frames: the streaming loop

Three ideas explain how frames leave the kernel.

  • A buffer is a block of memory big enough for one frame. The driver keeps a small set of them. We ask for four.
  • mmap (memory mapping) makes the driver's buffers visible inside our program's memory. Nothing is copied. The kernel and our program look at the same bytes.
  • To queue a buffer is to hand it to the driver, empty, to be filled. To dequeue is to take back one the driver has filled.

The loop itself is short. This is run() in dual_stream.py, without the preview lines:

def run(name, cam):                       # one thread per camera
    cap = cam["cap"]
    while not cam["stop"].is_set():
        if not select.select([cap.fd], [], [], 0.2)[0]:   # no frame yet: check the stop flag again
            continue
        index, _ = cap.dequeue_buffer()
        frame = cam["unpack"](cap.buffers[index]["mem"])  # a copy
        cap.queue_buffer(index)                           # the buffer goes straight back to the driver
        cam["last"], cam["frames"] = frame, cam["frames"] + 1

select() asks the kernel "is a frame ready on this file?" and waits at most 0.2 seconds for the answer. Without the time limit, a camera that stopped sending would leave the thread waiting forever and the program could not shut down.

Section 06

Processes, subprocess and pipes

Until 10 November 2026 the code did not read buffers itself. It started v4l2-ctl and read the frames from that program's output. Understanding why that was slow needs four terms.

  • A program is a file on disk. A process is a running copy of a program, with its own private memory. Two processes cannot see each other's memory.
  • subprocess is Python's standard module for starting another program from Python. subprocess.run([...]) starts it and waits for it to finish. subprocess.Popen([...]) starts it and lets it keep running alongside.
  • Every process has a standard output (stdout): the stream its printed output goes to. Normally that is the terminal.
  • A pipe is a one-way channel, provided by the kernel, that connects one process's output to another process's input. In a terminal you make one with |, as in dmesg | grep tevs. The kernel holds the bytes in transit in a buffer of 65,536 bytes. When it is full, the writing process is paused until the reader takes some out.

Readpipe(7) manual page (capacity, and what happens when a pipe is full) · Pipeline (Unix) (Wikipedia) · Python subprocess module

WatchUnix Pipeline (Brian Kernighan) Computerphile · Calling External Commands Using the Subprocess Module Corey Schafer

Where subprocess is still used, and why that is fine

Settings still go through v4l2-ctl and media-ctl, started with subprocess.run. Each call carries a few bytes and happens only when you change something, so its cost does not matter:

subprocess.run(["v4l2-ctl", "-d", cam["subdev"], "-c", f"exposure={us}"])

One frame path still uses a pipe: camera_API.py, the VizionSDK route on the Pi. It streams 1280 × 720 at 30 fps, about 55 MB/s, roughly a ninth of the colour camera's volume. Its speed has not been measured.

Threads

A thread is a second line of execution inside one process. Threads share the process's memory, so no pipe is needed between them. Each camera gets its own capture thread, so one camera never waits for the other, and the window runs on the main thread so it stays responsive. A threading.Event is the stop flag: close() sets it, then join() waits for the thread to finish before the buffers are released.

What happens when you run camera_ui.py

  1. The script builds the window. Each camera gets a title, a slot for the video, Size and Frame rate pickers, Exposure and Gain boxes, and an info line.
  2. Setting the starting size fills in the frame-rate list. That selection calls restart(name), which is what starts each camera.
  3. start() in dual_stream.py finds the camera by name, sets its format, sets exposure and frame rate with v4l2-ctl, calls open_capture(), and builds the small display pipeline. It returns a dictionary, cam, that describes the running camera.
  4. A capture thread runs run(name, cam): the loop from Section 05. The newest frame is always in cam["last"].
  5. About 15 times a second the thread also makes a small preview image and pushes it to the window.
  6. Once a second update_info() shows size, RAW10 and the frame rate counted over that second.
  7. Changing Exposure or Gain calls set_exposure or set_gain, which run v4l2-ctl while the camera keeps streaming. Changing Size or Frame rate stops and restarts that camera, which took under a second on the Jetson. measured
  8. Capture takes cam["last"] from each camera and saves it on a background thread, so the live view does not pause.
  9. Closing the window or pressing Ctrl+C calls close() for each camera.

The colour camera on its own

vc/imx412.py wraps the same steps in a class for scripts that only need the colour camera:

from vc import Camera, Mode, save, to_rgb8

with Camera(Mode(4032, 3040), exposure=30000) as cam:   # exposure in µs
    frame = cam.read()        # (3040, 4032) array of true 10-bit values, 0 to 1023
    info = cam.info()         # sensor, mode, controls, frame rate, device files, time
save(frame, "shot", info)     # shot.npy (exact values) + shot.json (how it was taken)

Frames are NumPy arrays: grids of numbers that Python can slice and do arithmetic on quickly. On the Pi, Mode can ask the sensor for a smaller rectangle (a crop) or for binning. On the Jetson the driver only delivers the full frame, so smaller sizes are cut out in Python and binning raises an error.

The TechNexion SDK route

An SDK is a library a vendor supplies for its own hardware. TechNexion's is pyvizionsdk. It lists the camera's RAW modes but can only stream UYVY, so camera_API.py keeps the SDK's functions and replaces four of them to stream RAW10 itself.

The SDK also refuses to find the camera on a CM5, because it only accepts the Pi 5's board name. vizion_cm5.py works around that with LD_PRELOAD: a Linux feature that loads a small library ahead of all others so its functions replace the standard ones. Ours replaces "open a file" so that, when the SDK reads the board name, it gets a file saying "Pi 5". Nothing else is changed. This route has not been ported to the Jetson.

Section 08 · Window and files

The live view

A raw frame looks wrong on a screen: far too big, dark, and for the colour camera, green. The live view applies a few cheap corrections to a shrunken copy. Saved files do not get any of this. They hold the sensor's values unchanged.

  • Sample. The preview is kept to about 1280 pixels wide. For the full colour frame that means taking one 2 × 2 block in every three, in each direction.
  • White balance. The sensor's green pixels respond more strongly than red and blue. The "grey world" method scales the three colours until their averages match.
  • Stretch. The brightest pixels (the 99.5th percentile) are mapped to white, so a dim scene still fills the display's range.
  • Gamma. Raising values to the power 1 / 2.2 brightens dark tones the way screens expect.

ReadGamma correction · Colour balance (Wikipedia; includes the grey-world method)

WatchComputer Color is Broken minutephysics (why gamma exists)

GStreamer and GTK

GStreamer is a library that builds video pipelines out of small parts joined with !. Ours has three parts per camera:

appsrc  !  videoconvert  !  gtksink
  • appsrc is a part that our own code feeds. run() pushes each preview image into it.
  • videoconvert changes the pixel layout into whatever the display part wants.
  • gtksink draws the video inside the window. dual_stream.py on its own uses autovideosink, which opens a window by itself.

GTK is the toolkit that draws the window, buttons and boxes. The constant DISPLAY_FPS = 15 in dual_stream.py sets how often a preview is made. It does not limit capture: every frame still passes through the capture thread.

Section 11

Drivers and boot setup

Neither camera's driver comes with the operating system. Each computer therefore needs two things done once, and again after every kernel update: build and install the driver modules, and add the cameras to the device tree so the kernel knows where they are.

Raspberry Pi

  • FL camera. scripts/build_camera_driver.sh downloads TechNexion's driver at a fixed revision, applies patches/tevs-raw.patch (which adds RAW output; UYVY stays the default), builds tevs.ko and compiles the overlays. sudo bash scripts/install_camera_driver.sh copies them into place and reloads the driver. Then /boot/firmware/config.txt needs camera_auto_detect=0 and dtoverlay=tevs-rpi22,cam0.
  • Colour camera. Vision Components ships a package that installs through DKMS, so it rebuilds itself on most kernel updates. Its config file must name the port, 4 lanes and Sony as the sensor maker. docs/vc-imx412-setup.md has the exact lines.
  • CM5 IO Board, CAM/DISP 1. That connector holds the camera's reset line high, so a TEVS plugged in there never starts. The fix is one wire from GPIO 4 through a 330 Ω resistor, plus the tevs-cam1-reset overlay. The README has the details.

ReadRaspberry Pi camera software (official docs) · TechNexion Pi driver · Vision Components Pi driver (GitHub) · DKMS (Wikipedia) · DKMS project

Jetson Orin Nano

  • The ABI check. An ABI is the exact memory layout that two separately compiled pieces of code must agree on. Our modules share data structures with NVIDIA's camera module. NVIDIA's header package lacks one generated file that affects that layout, so the repo carries a stand-in (jetson/include/nvidia/conftest.h). A wrong stand-in would still compile, and then corrupt kernel memory. The script proves it by building TechNexion's unmodified driver and requiring the result to match TechNexion's own binary instruction for instruction.
  • TEVS RAW10. TechNexion's Jetson driver only outputs UYVY. jetson/patches/tevs-raw10.patch makes a device-tree mode declared as 10-bit Bayer select the camera's RAW10 output.
  • The VC driver, cut down. Vision Components expects NVIDIA's camera module to be patched as well. We do not patch it. jetson/patches/vc-mipi-stock-tegracam.patch builds the driver against the unpatched module, which leaves out trigger mode, I/O mode, black level, binning and sensor cropping. Exposure, gain and frame rate work.
  • One overlay for both cameras. jetson/overlay/path-cameras.dts joins the two vendors' overlays, one camera each. A wrong overlay only shows up as a camera that does not start, so check_overlay.py compares every property with the vendors' files before anything is installed.
  • The boot entry. /boot/extlinux/extlinux.conf is the Jetson's boot menu. extlinux.py copies the existing "primary" entry into a new one that also loads our overlay, and makes it the default.

Section 12

Run it

On the Jetson

cd ~/src/PATH-Imaging
.venv/bin/python camera_ui.py                                   # both cameras live; Capture saves to ~/Desktop/PATH-captures
.venv/bin/python dual_stream.py                                 # both cameras for 60 s, then saves each one's last frame
.venv/bin/python scripts/capture_raw10.py --count 5 --png       # colour camera only

Do not use uv run or uv sync on the Jetson. The project file asks for Python 3.13, the Jetson has 3.12, and the virtual environment there was made by hand. uv run deletes it and fails to build a new one. If that happens, docs/jetson-orin-nano-setup.md has the two commands that rebuild it.

On a Raspberry Pi

uv run python camera_ui.py
uv run python scripts/capture_raw10.py --png
uv run python camera_API.py                  # FL camera through VizionSDK: 60 s live, saves raw10.pgm

Your user must be in the video and i2c groups. Quit with Ctrl+C, not Ctrl+Z: a paused run keeps the camera busy.

Section 13

Open problems

As of 10 November 2026.

ProblemWhat is known
Kernel faults while the colour camera streams (Jetson)The kernel log fills with memory-fault messages, about one per frame. Frames look intact. It never happens with the FL camera alone. The suspect is the sensor's two lines of embedded data; declaring zero lines stops the faults only because every frame is then discarded.
FL camera stuck in automatic exposure (Jetson)The camera can run in auto exposure while its exposure_mode control reads Manual. It then delivers 30.39 fps and ignores exposure. Setting exposure_mode to 1 and back to 0 cured it. What puts it in that state is not known.
FL camera at 1280 × 720 (Jetson)The kernel logs corr_err: discarding frame, also with plain v4l2-ctl. Not retested since the exposure cure above.
Pi code paths not rerunEach of vc/imx412.py, dual_stream.py and camera_ui.py gained a Jetson branch, and the pipe was replaced on both paths. None of it has been run on a Pi since.
Colour camera frame rate on the PiVision Components' Pi driver delivered 22.07 fps when asked for 30, so the code asks for 1.35 times the wanted rate.
Colour camera limited to 20 fps (Jetson)It is on the 2-lane port. Swapping ports is supported by the install script but untested.
Binning, sensor crop, black level (Jetson)Not available in our driver build. Measure the black level with the lens capped; do not assume the Pi's value of 64.
Trigger input removedRemoved from our code because the vendor manual lists none for the IMX412C. The driver source does contain a slave-sync mode.
camera_API.py not portedThe VizionSDK route runs on the Pi only.
Nothing committedThe Jetson port (jetson/, vc/tegra.py, the Jetson doc) and the direct-read change exist only in the working tree on the Jetson.

Section 14

Glossary

ABI
Application binary interface. The exact memory layout two separately compiled pieces of code must agree on.
appsrc
The GStreamer part that a program feeds with its own images.
Bayer pattern
The repeating 2 × 2 grid of red, green and blue filters over a colour sensor's pixels.
Binning
Combining neighbouring pixels on the sensor into one, giving a smaller and faster frame.
Bit depth
How many bits each pixel value has. Ten bits count from 0 to 1023.
Black level
The value a pixel reports with no light at all. It is not zero.
Buffer
A block of memory that holds one frame.
Control
A named number on a camera that a program can read or change, such as exposure.
Crop, ROI
Using only a rectangle of the sensor. ROI means region of interest.
CSI-2 (MIPI CSI-2)
The standard link that carries pixels from a camera to a small computer.
Decibel (dB, mdB)
A logarithmic unit for gain. 6 dB is about 2×, 20 dB is 10×. One mdB is a thousandth of a dB.
Demosaic
Working out full colour for every pixel from a Bayer frame.
Device file
An entry under /dev through which programs reach a device.
Device tree, overlay
A description of the board's hardware that the kernel reads at boot. An overlay is an add-on to it. Source files end in .dts, compiled ones in .dtbo.
DKMS
A system that rebuilds a driver automatically when the kernel is updated.
dmesg, journalctl -k
Commands that print the kernel's log, where drivers report what they found.
Driver
Kernel code that knows how to run one kind of device.
Exposure
How long the pixels collect light for one frame. Here it is given in microseconds.
extlinux.conf
The Jetson's boot menu file. Each entry names a kernel, a device tree and its overlays.
File descriptor
The small number the kernel gives a program to stand for a file it has opened.
FL
Fluorescence. Our name for the mono TEVS camera.
FourCC
A four-letter code naming a pixel format, such as RG10.
fps, mHz
Frames per second. One mHz is a thousandth of a hertz, so 20000 mHz is 20 fps.
Gain
Amplification of the pixel signal. It brightens the image and its noise alike.
Gamma
A curve that brightens dark tones for display. The preview uses a power of 1 / 2.2.
GPIO
A general-purpose pin the computer can switch high or low. Used here for a camera's reset line.
GStreamer
A library for building video pipelines from small parts joined with !.
GTK
The toolkit that draws the window, buttons and input boxes.
I2C
A slow two-wire bus for settings. Each chip on it has an address such as 0x1a.
ioctl
The system call that sends a command and a block of data to a device.
ISP
Image signal processor. Turns raw sensor values into a finished picture.
Jetson, L4T, JetPack
NVIDIA's small computer. L4T (Linux for Tegra) is its Linux; JetPack is the software bundle around it.
Kernel
The core of the operating system and the only software that talks to hardware.
Kernel module
A .ko file of kernel code that can be loaded separately, such as a driver.
Lane
One pair of wires in a CSI-2 link. More lanes carry more data per second.
LD_PRELOAD
A Linux setting that loads a chosen library first, so its functions replace the standard ones.
Media device, media-ctl
/dev/mediaN holds the map of how a camera's stages are linked. media-ctl shows and edits it.
mmap
Memory mapping. Makes a device's memory appear inside a program without copying.
NumPy, .npy
Python's library for arrays of numbers. A .npy file stores one array exactly.
Pipe
A one-way channel from one process's output to another's input, with a 65,536-byte buffer in the kernel.
Probe
A driver's start-up check that its device is present and answering.
Process
A running copy of a program, with its own private memory.
RAW10
Unprocessed sensor values with 10 bits per pixel.
SDK, VizionSDK
Software development kit: a vendor's library for its hardware. VizionSDK is TechNexion's.
select()
A call that waits, up to a time limit, until a file has something ready.
Sensor
The chip with the grid of light-detecting pixels.
stdout
Standard output. The stream a process's printed output goes to.
Sub-device
/dev/v4l-subdevN. One stage of a camera, usually the sensor, with its controls.
subprocess
Python's module for starting other programs.
Thread
A second line of execution inside one process, sharing its memory.
uv, virtual environment
uv is the Python project tool used here. A virtual environment (.venv) is a private folder of Python packages for one project.
V4L2
Video4Linux2. The kernel's standard interface for cameras.
v4l2-ctl
A command-line program that speaks V4L2: list cameras, change controls, grab frames.
White balance
Scaling red, green and blue so that grey things look grey.
YUY2, UYVY
Processed video formats that store brightness and colour separately. What an ISP usually outputs.
